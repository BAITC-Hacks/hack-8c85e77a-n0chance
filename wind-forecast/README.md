# WIND — Agentic AI для прогноза выработки ВЭС

Работающий MVP по кейсу HackAlem AI: почасовой прогноз нормированной мощности двух ветровых турбин на 24–48 часов, архив оперативной погоды, автоматическая проверка входных данных, выбор модели, пересчёт и rolling backtest.

**В исходном Word-файле есть условие, но нет таблицы измерений. Поэтому приложение запускается на явно обозначенных синтетических данных. Результат на настоящей ВЭС не заявляется.** Для завершения реальной оценки нужны история марта 2023 — января 2026 и фактические значения февраля 2026 от организаторов.

## Открыть на своём компьютере

1. На GitHub откройте папку `wind-forecast`. Предыдущий проект МОСТ находится в корне репозитория и работает отдельно.
2. Для скачивания всего репозитория: **Code → Download ZIP**, затем распакуйте архив.
3. В VS Code: **File → Open Folder → wind-forecast**.
4. В Windows дважды нажмите **START-WIND.cmd**. При первом запуске нужен Python 3.12 с опцией **Add Python to PATH** и интернет для установки зависимостей. На компьютере, где создан проект, окружение уже подготовлено.
5. Приложение откроется по адресу **http://localhost:5180**. Окно запуска оставьте открытым. Остановка — **Ctrl+C**.

Альтернативный запуск из терминала VS Code:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python app.py serve --open
```

macOS/Linux:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python app.py serve --open
```

После установки базовое демо работает без API-ключа и без сети. Внешний шрифт необязателен: при отсутствии сети используется системный. Приложение слушает только локальный адрес 127.0.0.1.

## Что показать на защите за 3 минуты

1. Откройте приложение: начальный прогноз строится автоматически. Покажите предупреждение о синтетических данных.
2. Переключите турбины, выберите 24 или 48 часов и нажмите **Рассчитать прогноз**. Наведите на график для просмотра часа.
3. Нажмите **Смоделировать обновление погоды**: прогноз и номер версии изменятся. Повтор обычного расчёта с теми же входами получает результат из кэша.
4. Нажмите **Запустить демонстрационную проверку**. Система выполнит 28 ежедневных расчётов и покажет MAE/RMSE отдельно по двум горизонтам и турбинам.
5. Скачайте прогноз в CSV, покажите журнал этапов и раздел источников.

## Настоящие данные

Нужен **CSV UTF-8 с разделителем-запятой**, одна строка на турбину и час. Excel-таблицу предварительно сохраните в этом формате и приведите названия столбцов к шаблону `examples/measurements.csv`. Шаблон содержит только четыре примера строк и не является достаточной обучающей историей.

| Столбец | Смысл |
|---|---|
| `timestamp` | Начало часового интервала, ISO 8601 с обязательным часовым поясом |
| `turbine_id` | `T1` или `T2` |
| `wind_speed_ms` | Средний ветер, м/с |
| `temperature_c` | Средняя наружная температура, °C |
| `power_normalized` | Средняя нормированная активная мощность, **0…1** |
| `available_at` | Необязательное время поступления измерения; по умолчанию конец часа |

Пример: `2026-01-31T22:00:00+05:00,T1,8.2,-3,0.31`. Если мощность в процентах, **заранее разделите на 100**. Время без часового пояса отклоняется; нельзя молча считать время UTC местным. Исторические казахстанские измерения должны содержать реальное смещение на свою дату: до смены времени в 2024 году оно могло отличаться. Для расписания февраля 2026 используется UTC+5.

Файл можно загрузить кнопкой в приложении. Загрузка переключает его в реальный режим; синтетическая погода к вашим измерениям не подмешивается. Загруженный CSV хранится только в памяти до остановки сервера. Прогнозы и журнал сохраняются локально в `runtime/`, которая исключена из GitHub. Не помещайте частные данные в исходники.

Минимум для расчёта — 168 корректных исторических часов каждой турбины. Неполные строки, NaN, дубли, неизвестные турбины, недопустимые диапазоны и недостоверное время доступности отклоняются с номером строки. Пропуски часов в обучении допустимы; скрытого заполнения целевой мощности нет. Для боевой оценки проверьте покрытие всей истории, единицы и высоту датчика.

## Оперативный архив погоды NOAA

Дополнительные зависимости:

```sh
python -m pip install -r requirements-weather.txt
python app.py weather --issue 2026-01-31T23:00:00+05:00 --horizon 48
python app.py forecast --real --measurements data.csv --weather-file runtime/weather.json --issue 2026-01-31T23:00:00+05:00 --horizon 48
```

В активированном окружении команда `python` означает Python из `.venv`; на Windows без активации замените её на `.venv\Scripts\python`.

Можно пропустить `--weather-file`: система сама загрузит NOAA GFS. При ошибке сети или отсутствии корректного архива расчёт завершится ошибкой; замены на реальные наблюдения или синтетическую погоду нет. JSON погоды предназначен для повторного использования файла, созданного этим провайдером, а не для импорта произвольного источника.

Координаты из ссылок кейса:

- T1: 43.645150 N, 78.535604 E.
- T2: 43.643198 N, 78.538828 E.

Алгоритм выбирает последний запуск GFS с запасом шесть часов на выпуск, проверяет `Last-Modified` каждого файла и индекса относительно момента расчёта и при необходимости пробует два предыдущих запуска. Это консервативный выбор: более свежий уже доступный запуск иногда пропускается. `run_at` сам по себе не считается доказательством доступности. Объекты, перепубликованные после момента расчёта, тоже отклоняются.

Из GRIB2 загружаются **только диапазоны байтов** для U/V ветра на 100 м и температуры на 2 м. Проверяются HTTP 206, Content-Range, время запуска, горизонт, переменная и высота GRIB. Сохраняются URL, ETag, время публикации и SHA-256 диапазона. Декодер — ECMWF ecCodes. `--height 10` позволяет использовать ветер на 10 м в CLI; в интерфейсе фиксировано 100 м. Высоту нужно согласовать с предоставленными измерениями.

Сетка 0,25° грубее расстояния между турбинами: обе получают погоду из одного ближайшего узла (43.75 N, 78.5 E). Модели мощности обучаются отдельно. Микрорельеф, след турбины, обледенение, техническая доступность и диспетчерские ограничения пока явно не моделируются. Мгновенный NWP на начало часа используется как приближение для среднего за час; это нужно учитывать при реальной калибровке.

**Не используем реанализ, погодные наблюдения будущего или hindcast вместо оперативного архива.** В частности, у альтернативных API дата начала архива может быть позже февраля 2026 или длинная история может оказаться hindcast. Указание «historical» само по себе не гарантирует правильный rolling backtest.

Первый полный архив на 48 часов — примерно 140 МБ сетевого трафика, хотя сохраняются только извлечённые значения и метаданные. Полный февраль может потребовать несколько ГБ и длительное время. Последующие обращения используют локальный кэш.

## Модели и защита от утечки

- История фильтруется по `available_at <= issue_at` и `timestamp < 2026-02-01T00:00:00+05:00`.
- Для каждой турбины используются последние 2160 доступных строк (до 90 дней при непрерывных часовых данных).
- Хронологическое разделение 80/20: три RBF ridge-модели с регуляризацией 0.01, 0.3 и 3. Выбирается минимальный MAE; случайного перемешивания нет.
- Входы — нелинейные функции скорости ветра и температура. Обучение сейчас на **измеренном ветре**, а применение на NWP: это ограничение и источник сдвига распределения.
- Если валидация хуже среднего исторического значения, агент выбирает прогноз средним. Финальная модель обучается на всей доступной предфевральской истории.
- Предсказания ограничиваются диапазоном 0…1. Установленная мощность турбин в условии не дана, поэтому интерфейс **не выдаёт выдуманные МВт или МВт·ч**. При известном номинале: `power_MW = power_normalized × rated_MW`; энергия за час — MW × 1 h.
- Полоса на графике: ±90-й перцентиль абсолютного остатка на хронологической валидации, обрезанный до 0…1. Это диагностический диапазон ошибки на измеренном ветре, **не калиброванный вероятностный интервал NWP**.

## Февральская проверка

```sh
python app.py backtest
python app.py backtest --real --measurements history-and-february.csv
```

Вторая команда требует настоящих измерений февраля только для оценки; модуль прогнозирования не использует их для обучения. Без фактических февральских значений прогнозы будут построены, но метрики отсутствуют. Число реально сопоставленных наблюдений указано в `n` для каждой группы.

28 моментов расчёта: 31 января 23:00, 1 февраля 23:00, …, 27 февраля 23:00 по UTC+5. Каждый прогноз — следующие 48 часов. Горизонт 1–24 покрывает 672 уникальных февральских часа на турбину; 25–48 — 648, поскольку последние 24 часа выходят в март и исключаются. Перекрывающиеся горизонты не смешиваются в одну метрику.

MAE = среднее `|prediction − actual|`; RMSE = корень из среднего квадрата ошибки. В JSON единицы 0…1, в интерфейсе — процентные пункты номинала. Для сравнения сохраняется persistence: последнее измерение мощности, доступное до расчёта в предфевральской истории. Выводятся покрытие диагностической полосы и число наблюдений. MAPE не используется из-за нулевой мощности.

Синтетический сценарий детерминирован (seed 2026), содержит общую искусственную погоду, шум измерений, разные кривые мощности турбин и шум прогноза. Он проверяет работоспособность, но не доказывает качество модели на реальной погоде.

## Что делает агент самостоятельно

Это **детерминированный агент с инструментами**, без LLM и без платных API. Он проверяет данные, получает архив, отклоняет недоступные запуски, повторяет сетевые запросы, выбирает модель по прошлой валидации, применяет запасной метод, сохраняет прогноз и журнал. Файлы результата версионируются по SHA-256 входов и параметров; одинаковый запрос использует кэш. Обновлённые входы запускают новый расчёт.

Для автоматического наблюдения за обновляемыми локальными файлами:

```sh
python watch.py --measurements data.csv --weather-file runtime/weather.json --issue 2026-01-31T23:00:00+05:00 --horizon 48 --interval 60
```

Это процесс до Ctrl+C, не системная служба. Он наблюдает одну фиксированную историческую дату; поставщик должен обновлять JSON атомарно. Повреждённый файл не затирает последний успешный прогноз. Для смены момента расчёта перезапустите с новым `--issue`. `--cycles 1` выполняет один проход.

## Файлы проекта

- `app.py` — HTTP-интерфейс и CLI, импорт/экспорт.
- `wind/core.py` — качество данных, модели, агент, backtest и синтетический сценарий.
- `wind/weather.py` — оперативные архивы NOAA, ecCodes и доказательства происхождения.
- `watch.py` — пересчёт при обновлении файлов.
- `web/` — адаптивная панель на русском языке, интерактивный SVG-график.
- `tests/` — независимые от сети проверки времени, утечек, покрытия и пересчёта.
- `runtime/runs/` — версии прогнозов и `audit.jsonl`; `runtime/weather/` — извлечённый погодный кэш.
- `runtime/result.json`, `runtime/forecast.csv` — последний результат CLI.

## Воспроизводимость и ограничения

```sh
python -m unittest discover -s tests -v
```

14 автоматических тестов проверяют доступность измерений и погоды, запрет реанализа/синтетики в реальном режиме, неизменность прогнозов при изменении будущих ответов, границы мощности, дубликаты/NaN, часовые пояса, резервный запуск NOAA, полный февральский календарь и смену версии при обновлении погоды. Прямое скачивание и декодирование архивного NOAA проверены отдельно; тесты CI не зависят от сети NOAA.

Это локальный исследовательский MVP, не система управления реальной ВЭС. Нет многопользовательской авторизации, серверной очереди задач и производственного мониторинга. Импорт CSV не включает автоматическое распознавание произвольных Excel-колонок. Реальные метрики, калибровка на историческом NWP, анализ зимних остановов и качество по горизонтам требуют таблиц организаторов. Полный реальный февральский прогон ещё не выполнен.
